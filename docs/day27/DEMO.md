## 1. 展示目標

讓觀眾看見：使用者確認後才建單；暫停保留原單並阻擋認領；恢復後認領一次；重送查回同號。螢幕上的完成狀態必須能對回資料庫。

本機備援展示相同規則，但只操作合成身分與 SQLite。它不發送 LINE 訊息、不呼叫 Gemini，也不驗證 Firestore 交易。

## 3. 開場前檢查

- 確認測試帳號、角色與合法來源資料，正式客戶帳號不作展示測試場。
- 檢查模式標籤：`LIVE`、`MOCK_LOCAL`、`OFFLINE_SQLITE`、`PRERECORDED`。
- 模型呼叫、推播與雲端寫入需由操作人員確認權限、預算與停止方式。文件本身不授權呼叫。
- 檢查 LINE 內建自動回應設定，避免官方帳號與程式同時回覆造成誤判；保留合適歡迎訊息。
- 先安裝本機所需 Python 與程式，再確認播放裝置能離線開啟備援影片。
- 公開展示隱去權杖、金鑰、電話與私人識別。單號可在受控畫面顯示；公開素材保留可對帳但去識別的對照。

## 4. Google Cloud Shell 操作路徑

用瀏覽器開啟 Cloud Shell。先確認可使用 Docker 與 Git；使用本篇隨附的 `day27_cleanroom.sh`，或複製正文第三節完整命令執行。


這會建立新的 `$HOME/local-demo-時間/` 資料夾，取得固定公開版本。建置時允許網路下載；測試容器使用 `--network none`，只掛載新的報告資料夾。

## 5. 雙手機 0～180 秒劇本

下表是拍攝與現場操作規格，尚非實機日誌。先完成 Firestore 接線、角色授權、通知與查回，才可使用 `LIVE` 標籤。

| 時間 | 講者台詞 | 操作 | 實機合格證據 |
|---|---|---|---|
| 0～30 秒 | 先看版本，再看今天要交給誰。 | 指出固定版本與當次執行報告。 | Commit、測試範圍、部署與素材版本可對照。 |
| 30～75 秒 | 提問是意圖，按確認才是同意。 | A 問「花壇走讀幾點集合？」；查看工具結果，核對並確認詢問；B 看通知。 | 查詢不得把活動時間冒充集合時間；確認後才建立權威 request_id；B 卡片同號。 |
| 75～120 秒 | 已存在的單要留著，新認領先停下。 | 管理者 PAUSED；B 點「我來處理」被拒；SERVING 後再認領。 | 單據暫停前後不變；成功認領後版本增加；呼叫者為授權志工。 |
| 120～180 秒 | 他看到的進度，要是同一張單的現在。 | A 查回 human_claimed，再點原確認卡。 | 本人授權查回、同號、無第二張單；受理不代表店家供餐承諾。 |

### 版本與資料條件

權威單據使用既有 Firestore `requests` 文件；不能把 SQLite UUID 當作同一張雲端單。Day 11 查回與 Day 13 回條的狀態限制需要在實際接線版本調整並驗證；不可僅放寬全部欄位檢查。

同一個 `request_id` 的證據需串起使用者確認、通知接受回條、B 看見、暫停拒絕、認領前後版本與 A 查回。`operation_key`、`X-Line-Retry-Key` 與服務單號各有用途，不必是同一字串。

## 6. 故障切換決策

本次舞台等待額度選為 10 秒。這是講解節奏，不是請求期限或後端已取消的證明。

| 狀況 | 先做什麼 | 接替路徑與台詞 |
|---|---|---|
| LINE 或 Webhook 等待超額 | 停止重複點擊，保留操作識別與單號，依實際接受狀態查回。 | 「這筆目前先保留未知，我改示範已備妥的本機規則。」 |
| 模型限流或上游錯誤 | 保存狀態與用量；不為趕畫面臨時改模型或提高預算。 | 若有已驗證本機模擬處理器，使用 `MOCK_LOCAL`；否則跳過。 |
| 會場完全斷網 | 不進行新雲端請求，保留前一個雲端案件狀態。 | `OFFLINE_SQLITE`：另起合成示範，清楚說明不是線上單。 |
| 手機投影或電腦硬體異常 | 不拼接假聊天畫面。 | 有已驗收離線影片才使用 `PRERECORDED`，否則停在架構解說。 |

接受狀態未知的推播，依原內容、收件人與原重試鍵處理；已確認被 LINE 接受的請求不再另換鍵重派。恢復網路後先對帳，不把本機資料寫回雲端頂替結果。

## 7. 備援錄影的驗收規格

影片檔目前沒有提供。錄影規格已定，完成錄影後另外留下實際狀態。

錄影同時包含兩支手機與終端畫面，開始顯示錄製日期、程式與部署版本。用一段連續畫面保留從確認、通知、暫停、恢復到查回的流程；不剪掉失敗、等待或重試以假裝一次完成。

私密原始檔與公開遮蔽副本各留雜湊。若在公開副本遮蔽個資，標明已遮蔽，且不可遮掉關鍵狀態與時序。兩人分別操作時才稱兩位操作人員；同一人持兩個測試帳號應據實標明。

上台前將影片下載到播放裝置，在斷網狀態完整試播；YouTube 不公開連結僅作分享入口。播放台詞：

> 現在切換成先前實際錄下的備援影片；錄製日期與版本顯示在畫面上。

影片狀態、檔案雜湊、時長、來源版本、角色說明、去識別說明、對應 request_id 與實際播放測試，均由真正錄製和播放結果填寫；缺少時不能把狀態設成 READY。

## 8. 本機 SQLite 路徑

將隨稿 `replay_day27.py` 放在固定 Repo 根目錄，在 Python 3.10+ 的本機環境執行。此路徑只使用標準函式庫及 Day 22 核心，與執行全套 155 項測試所需的 Pydantic 環境不同。

```bash
python3 replay_day27.py --out out/day27/replay-normal
python3 -O replay_day27.py --out out/day27/replay-optimized
```

輸出目錄必須不存在。預期各次輸出：`status=PASS`、`request_count=1`、`final_state=human_claimed`、認領版本 1→2、第二次認領 false、原操作查回同號。兩次執行各有自己的單號。

程式在執行前核對固定 Day 22 核心檔案 SHA-256；不符即拒絕。成功與失敗各自留 `report.json`；既有資料夾或版本不符則在建立新資料前拒絕。本次已在獨立 Linux／Python 3.13.5 環境執行上述兩種模式，另有 5 項本機檢查；沒有套用 OS 斷網隔離，也沒有呼叫外部服務。

將隨稿 `test_day27_replay.py` 也放到同一個 Repo 根目錄，即可重跑上述 5 項獨立檢查。測試只建立 `out/day27/replay-tests/` 內的暫存資料，結束後清除該次暫存子目錄，不操作正式資料。

```bash
python3 -m unittest test_day27_replay -v
```
